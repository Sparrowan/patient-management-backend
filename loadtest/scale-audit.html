Six countries,
one write primary

The load test measured a laptop. This is the question underneath it: does this architecture get faster when you give it more machines? Mostly yes — and the exceptions are specific enough to name, one of which is switched on right now.

Verdict

The shape is right. Three things won't scale by buying hardware — and only one of them is hard.

Stateless services, a database per service, background workers that claim work with SKIP LOCKED, and idempotency at two levels. That combination is what makes "add replicas" a real answer rather than a hope, and most projects of this size don't have it.

What stops it is not the code you've written. It is one Kafka partition (live today, invisible until you scale out), connection-pool arithmetic (tunable, ~14 instances per database), and a single write primary per service — the only genuinely architectural one. For a six-country deployment, that last wall is likely solved for you by regulation before you ever have to build sharding.

What the load test actually proved

And, more usefully, what it didn't

Both curves below were measured on the same saturated box, so the absolute numbers describe this laptop and nothing else. The relationship between them is the finding.

A JWT-verified, cache-backed, JSON-serialising read reaches 78% of the throughput of an endpoint that does nothing at all. Every piece of security, business logic and serialisation you wrote costs about a fifth of the budget. The application is not the expensive part.

The expensive part is the host, and it can be shown rather than asserted. During the 200-connection run the containers accounted for roughly 3.6 of 8 cores, while the host had 0.7% idle CPU and 57.5% of it in the kernel — that missing time is the load generator plus the virtualisation and network layer, not your services.

Note the shape at the right-hand edge: doubling offered load from 100 to 200 connections halved throughput and multiplied p95 latency by seven, with zero failed requests. That is queueing, not breakage — and it is why "throw more concurrency at it" is the wrong reflex, and why a benchmark reported at a single concurrency level tells you nothing.

What scales by adding machines

Verified in the codebase, not assumed
Stateless services JWTs verified locally against JWKS. No session store, no sticky sessions — any replica serves any request.
Database per service No shared database to become the common bottleneck. Blast radius and capacity are both per-service.
Outbox relay SELECT … FOR UPDATE SKIP LOCKED — N replicas claim disjoint batches. No double publish, no blocking.
Payout saga worker Same claim pattern, backed by idx_payouts_due so the lock is row-precise rather than over-broad.
Rate limiting Token-bucket state in Redis, so the limit holds across gateway replicas instead of per-instance.
Read replicas Routing by readOnly, with a per-query escape hatch for reads that must not be stale.
Keyset pagination O(limit) at any depth, no COUNT. Deep pages cost the same as the first one.
Ledger archival Bounds the hot working set on a table that may never be deleted from.
Two-level idempotency The quiet precondition for all of it: scaling out means retries, and retries are only safe if replaying is.
Transactional outbox No dual write. Event delivery survives crashes, which is what lets instances be disposable.

What doesn't

Three walls, in ascending order of difficulty
Live now

Kafka runs on one partition

$ kafka-topics --describe --topic patient-events Topic: patient-events PartitionCount: 1 ReplicationFactor: 1

Consumer parallelism inside a group is capped by partition count, not by replica count. Scale billing-service to ten instances today and nine of them sit idle on this topic while one does all the projection work.

This is the most dangerous class of scaling bug, because a single instance works perfectly — the defect only appears at the exact moment you reach for the fix. Nothing in a dev environment will ever reveal it.

Raising the count is the fix, and keying by aggregate id already preserves per-aggregate ordering across partitions. Two cautions: partitions can be added but never removed, and adding them re-maps keys to partitions, so events for one aggregate can briefly land out of order across the change. Size it once, deliberately, above your expected consumer count.

Tunable

Connection-pool arithmetic caps instance count

HikariCP maximum-pool-size 10 (Spring default, undeclared) MariaDB max_connections 151 replicas × pool_max < max_connections − headroom 14 × 10 = 140 · 151 − 10 = 141 ← ceiling

About fourteen instances per database, and exhaustion does not announce itself — it presents as connection-acquisition timeouts under load, which read like a slow database rather than a misconfigured pool.

Worth internalising the counter-intuitive half: a bigger pool is usually worse. Small pools (10–20) generally outperform large ones, because the database can only execute so much concurrently and a deep pool just relocates the queue somewhere you can't see it. The lever to reach for first is open-in-view=false — already set — which returns connections at the end of the service method instead of the end of the request.

Architectural

Every write lands on a single primary

Read replicas, the Redis cache, keyset pagination and ledger archival all push this wall further away. None of them move it. Every registration, credit, debit, transfer and payout still terminates at one primary per service, and that primary is the ceiling on write throughput no matter how many application instances front it.

This is the honest answer to "will it scale if I add resources": reads scale by copying, writes do not. Beyond this point the lever is sharding — splitting the data tier by key — which is the most invasive change in the catalogue and is not built here.

The trigger is worth stating precisely, because it is widely misunderstood: you shard when write throughput exceeds one primary or the working set exceeds RAM. Not when the row count gets large. A single indexed InnoDB node is comfortable at hundreds of millions of rows — an indexed lookup costs three to five page reads whether the table holds a million rows or a billion.

Three things that aren't walls but will bite

Operational, and cheap to fix before they matter
Deploy-time

Every scheduled job fires on every instance at startup

@Scheduled(fixedDelay=…) with no initial delay runs immediately on context start. That is convenient — it is how the archival sweep was verified live by restarting a container — but during a rolling deploy of N replicas it means N simultaneous sweeps. Safe here, because each job is either SKIP LOCKED-claimed or idempotent. Still a shape to recognise: it is a thundering herd that scales with your replica count.

Availability

The synchronous delete veto has no circuit breaker

Resilience4j was removed along with the old gRPC client when registration moved to Kafka, and the surviving synchronous call — CloseAccountForPatient — never got it back. A 3-second deadline bounds each call, but under a billing-service brownout every delete waits the full three seconds before failing. Across regions, that coupling gets considerably more expensive.

Known gap

No service discovery or config server

Service addresses are environment variables today, which is fine at four services and becomes unmanageable well before it becomes dangerous. Already on the roadmap; Kubernetes-native discovery would make it a non-decision.

What six countries actually changes

Where the interesting problems move to

The instinct that a multi-country deployment is "the same thing, bigger" is the one worth discarding early. Almost none of the difficulty is throughput.

Residency

Several markets require that personal and financial data stay in-country. That forces per-country deployments — which is sharding, with country as the shard key, handed to you by a regulator instead of designed by you. Each country gets its own write primary, and the wall above stops being the binding constraint without your building a global sharding layer.

The global remainder

Once per-country is the default, the design question inverts: what, if anything, is global? Cross-border transfers, FX, group-level reporting, a customer who exists in two markets. That small remainder is where the sagas, the settlement logic and the reconciliation live — and it is the genuinely hard engineering.

Multi-currency

A correctness concern, not a scaling one. Amounts must never be summed across currencies — CurrencyMismatchException is the right instinct already in place. What's missing is everything around a rate: which rate applied, when it was valid, and who bore the spread. Those become ledger facts, not lookups.

Call locality

The synchronous gRPC veto costs milliseconds inside one region and a hundred-plus across them, while coupling availability across a border. The rule that follows: synchronous calls stay in-region; anything crossing a border is asynchronous, with a visible pending state.

Retention

Retention windows differ by jurisdiction, so the ledger archival cutoff and the idempotency TTL become per-country configuration rather than constants. Both were built as configuration already, which is the useful part.

How to actually prove it

In order, because each answers the previous one's question

  1. Raise the partition count, then run two consumers. Verify the work splits. This is the one live defect, and it is also the cheapest possible experiment: scale the consumer to two instances and watch whether both do work.

  2. Re-measure where the box isn't the bottleneck. One instance, then two, then four, on hardware with the load generator somewhere else. The claim is linear scaling; it is worth having measured rather than believed. Everything on this laptop is confounded by 0.7% idle CPU.

  3. Load the write path separately. Credits against one account versus spread across many isolates pessimistic-lock contention exactly. Expect a far lower ceiling than reads, and expect that to be correct behaviour rather than a defect.

  4. Then size it. With a real per-request cost from step 2, the instance count, database capacity and connection budget for a target rate is arithmetic. Doing that calculation from measurements you trust is the defensible version of "yes, it scales".
